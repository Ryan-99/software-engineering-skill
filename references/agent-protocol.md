# Coding Agent 协作协议

SKILL.md 定义门禁与文档；本文件定义执行期的 Agent 编排细节：角色的出厂配置与物化、上下文分配、派发循环、生产纪律、代码库约定。实现类子代理配合 `subagent-driven-development` 的流程（每任务新代理 + 两段评审 + 评审循环）。

## 角色出厂配置与物化

四类角色的提示词模板随技能出厂，位于 `~/.agents/skills/software-engineering/assets/agents/`：

| 模板 | 角色 | 派发时机 |
|---|---|---|
| `implementer.md` | 实现代理 | 每任务一个全新代理 |
| `spec-reviewer.md` | 需求符合评审 | 实现报告后、质量评审前 |
| `quality-reviewer.md` | 质量评审 | spec 评审通过后，评审 BASE..HEAD diff |
| `explorer.md` | 勘察代理 | brownfield G2 前；任何大范围读码问题 |

**首次调用物化**（EXEC 步骤 0，或用户说"先把 agent 建起来"）：

```bash
node ~/.agents/skills/software-engineering/scripts/scaffold_agents.mjs <项目根>
```

幂等复制到 `<项目根>/.agents/`（已存在跳过不覆盖，项目内修改不会被冲掉）。之后控制器逐份裁剪占位符【】——贴入本项目的技术栈、验证命令、约定——再按模板填任务信息派发。技能内 assets 是出厂正本，项目内 `.agents/` 是项目实例。

## 岗位 → Agent 编排映射

| 传统岗位 | Agent 时代对应 | 要点 |
|---|---|---|
| 项目经理 | 主会话 | 门禁编排、用户沟通、pipeline.json 落账 |
| 架构师 | 主会话 + 勘察代理 | 设计在主会话做；代码库勘察外包，结论落 ARCHITECTURE |
| 开发工程师 | 实现代理 | 每任务一个新代理，提示词自包含 |
| 评审 | 需求符合评审 + 质量评审两段 | 先对照规格逐条核，再看代码质量 |
| 测试/QA | 机械门禁 + E2E 代理 | typecheck/lint/test/check_gate 可命令化；Web E2E 用 web-gui-tester |
| 配置管理 | git + pipeline.json | commit 带任务编号；状态即刻落账 |
| 运维/发布 | 用户 | L2 边界：对外发布只出方案等人执行 |

## 上下文纪律（五条）

1. **控制器不写业务代码**。主会话的上下文留给门禁判断、任务编排、用户沟通；亲手写实现，编排判断力就被实现细节淹没（上下文污染）。
2. **子代理默认零记忆**。每次派发都是全新上下文：提示词必须自包含——任务卡全文、涉及文件路径、相关接口契约、验证命令、全局约束。不写"参照之前""如上次所说"。
3. **文档按需切片**。任务提示词 = 任务卡全文 + 模块地图相关行 + Interfaces 签名原文，不整读 ARCHITECTURE/REQUIREMENTS。文档表格化、条目化就是为了能按行切片。
4. **大勘察外包**。需要读大量文件才能回答的问题派勘察代理（`explorer.md`），要求只回结论；结论落文档，过程细节不进主会话。
5. **冷启动三件套**。任何新会话接手 = 读 pipeline.json → 跑 check_gate → 读 PLAN 未完成任务卡。不依赖任何聊天记忆。

## 生产纪律（实现与验证的底线）

- **TDD 红绿循环**：先写失败测试、看它失败（RED），再写最小实现通过（GREEN），重构保持绿。没看过失败的测试等于没证明它能抓 bug；测试立即通过 = 在测旧行为。修 bug 必走此路，失败测试留作回归。轻量档可按项目裁剪，完整档默认强制。
- **全量绿才算绿**：只跑自己写的那个测试文件绿 ≠ 全量绿；套件里任何失败（哪怕不是你造成的）必须在报告点名——漏报的红测试等于造假。
- **先证据后断言**：宣称"完成/通过/修复"必须有本次会话新跑的命令输出为据；"应该没问题""看起来对了"都是违规表述。代理自述不算证据。
- **根因先行**：修任何 bug 前先读错误全文、稳定复现、查最近变更；没完成根因调查不许提修复方案，猜着改 = 返工。

## 派发循环（每任务）

1. 控制器取任务卡，按 `implementer.md` 填全占位符派实现代理。代理对需求有疑问**开工前就问**，控制器答完再放行。
2. 实现报告回来 → 按 `spec-reviewer.md` 派需求符合评审：不信自述、逐行读代码对照规格，产出 符合/问题清单（缺失/多余/误解，带 file:line）+ 搁置清单。
3. spec 通过 → 按 `quality-reviewer.md` 派质量评审：BASE..HEAD diff 只读评审，产出 优点/问题（Critical/Important/Minor）/搁置清单/结论（是、否、修后可）。两份评审的搁置清单由控制器逐条裁决，不许静默丢弃。
4. 评审有问题 → 原实现代理修 → 复审，循环直到双绿。
5. **控制器亲自跑验证命令与全量门禁**（不信任何自述）→ 绿了更新 PLAN 状态列 + commit（`G3-T1: …`）。

## 失败与升级协议

- 评审不过 → 原实现代理修 → 复审（见上）。
- 子代理中途异常或跑偏 → 派新代理，提示词附上次失败的产出与原因；**禁止主会话亲手修实现代码**。
- 同一任务连续失败 2 次 → 停止重试，升级用户：附失败摘要、已试方案、2 个候选出路。
- 测试失败 → 缺陷落 TEST-REPORT 缺陷表闭环，不允许"顺手口头修"不落账。

## 工作区隔离协议（Git）

执行期改动要隔离：不污染用户当前工作区，也不与并行工作互相踩。现在项目不只存在于本地——远端协作是常态，隔离与整合都要按"会推远端"的标准做。

1. **检测现状**：`git rev-parse --git-dir` 与 `--git-common-dir` 不同 = 已在 linked worktree（另查 `--show-superproject-working-tree` 排除子模块误判）——直接用现有隔离，不重复建。
2. **选隔离方式**（用户已表达的偏好优先于默认）：
   - **默认：feature 分支** `sdlc/<项目名>`——单人单线最简单，当前检出直接切。
   - **并行推进 / 不想动当前检出：git worktree**——目录默认 `.worktrees/<分支名>`；先 `git check-ignore -q .worktrees` 确认已忽略（没忽略就补 .gitignore 并 commit，否则整个 worktree 会被提交进仓库）；`git worktree add .worktrees/<分支> -b <分支>`；worktree 里依赖**单独安装**（Node 项目各自 npm install）。
3. **基线验证**：隔离就绪后跑一次全量测试。基线红先报告用户再动工——脏基线让之后所有失败都变得模糊。
4. **远端协作**：有 remote 时执行开始记录远端与默认分支；长任务建议日推分支防丢失；推送与 PR 属收尾整合菜单，不经用户选择不主动 push。

## Agent 可导航代码库约定（脚手架阶段建立）

- 项目根放 `AGENTS.md`（模板见 templates.md）：一句话定位 + 目录地图 + 常用命令（构建/测试/门禁校验）+ 硬约定。任何 Agent 进项目第一读它。
- 命名可 grep：标识符用完整语义词，避免魔法缩写；提示性字符串常量集中定义，不散落拼接。
- 单文件尺寸自律（约 >500 行拆模块）：Agent 的定位与修改精度随文件增大而下降。
- 公共接口写契约注释：行为约定、参数边界、错误语义——这是 Agent 查阅代码时最依赖的信号。
- 测试名写成行为规格句（"登录失败五次锁定账户"，而非 `test_1`），让测试目录可当行为文档检索。
- 目录即语义：模块目录名 = 模块地图条目名，保持一致，Agent 从地图可直接定位目录。

## Brownfield 勘察协议（在既有代码库上开工）

1. G2 之前按 `explorer.md` 派勘察代理（very thorough 级）摸现状：模块清单、入口文件、关键依赖、技术债信号。
2. 结论写成 ARCHITECTURE.md 的"现状模块地图"，与目标设计对照标注改动面。
3. 勘察结论同样过 G2 确认——用户确认的是基于真实现状的设计，不是 Agent 想象的项目。

## 收尾整合（G4 前置）

全任务完成 → 跑全量测试 → 向用户出三选一（整合决策归用户，L2）：

1. **本地合并回主干**：切回主干 → 合并 → **合并结果上复跑全量**（绿只证明它跑过的那棵树；合并结果红了就停下排查，分支与 worktree 原地保留——没推送过，本地可恢复）→ 绿了删除 feature 分支并清理 worktree。
2. **推远端建 PR**：`git push -u origin <分支>`，本机有 gh 直接建 PR 并回报 URL，没有就把 forge 打印的创建链接给用户。**保留分支与 worktree**——PR 反馈要在上面继续改。
3. **保留待处理**：报告分支名与 worktree 路径，不动。

**worktree 清理规则**：只清理自己建在 `.worktrees/`（或 `worktrees/`）下的，别的来历一律不动；`git worktree remove` 被拒 = 里面有未提交文件——`git status --porcelain -uall` 列出内容，给用户三选一（提交进分支 / 移回主仓库 / 删除（不可恢复）），执行选择后再清，**禁止主动 `--force`**。丢弃整个分支的工作只响应用户明确要求，且先列出将永久删除的分支、commit 列表、worktree 路径，等用户确认后才执行。
